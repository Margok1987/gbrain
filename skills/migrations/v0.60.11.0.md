# Upgrade to v0.60.11.0: preview the recovery plan, then apply what the user agrees to

This release wires the `gbrain repair` kinds into doctor's remediation plan and
run, adds a preview-only recovery banner to `gbrain post-upgrade`, shows remote
callers one host-action line per recovery check, records which gbrain version
admitted and published each write, and adds an opt-in writer admin lock and an
operator autopilot pause. Schema migration v191 adds five nullable columns to
`persistence_requests` (`admitter_version`, `admitter_host_id`,
`consumer_version`, `consumer_host_id`, `published_at`) and records the
cutoff with the database clock. It deletes nothing and starts no service.

Never apply a repair, raise a limit, lock, unlock or resume on the user's
behalf without asking. Every step below that changes the brain needs the
user's agreement first.

1. **Upgrade hosts in order, with autopilot paused.** List with the user every
   host that uses this brain. On each host that runs connector jobs, pause
   autopilot first; upgrade the hosts that run the persistence consumer or own
   a worktree before the connector hosts; then resume:

   ```bash
   gbrain autopilot pause --reason "upgrading to v0.60.11.0"   # each connector host
   gbrain upgrade                                              # consumer and worktree-owner hosts first
   gbrain upgrade                                              # then connector hosts
   gbrain doctor --remediation-plan                            # step 3
   gbrain autopilot resume                                     # each host you paused
   gbrain sources status                                       # verify
   ```

   The pause survives `gbrain upgrade`. If schema work did not complete, run
   `gbrain apply-migrations --yes --no-autopilot-install` on the brain host.

2. **Relay the post-upgrade banner.** When `gbrain post-upgrade` prints an
   `[AGENT] Relay this to your operator` block, show it to the user as-is. It
   lists each finding and its count and never applies anything.

3. **Preview the recovery plan and ask.**

   ```bash
   gbrain doctor --remediation-plan
   ```

   Show the user the repair steps (each marked "requires user agreement"),
   their estimated cost, and the combined command at the end. Ask which to
   apply and what spending cap they accept.

4. **Apply only what the user agreed to**, with their cap:

   ```bash
   gbrain doctor --remediate --yes --include-repairs --max-usd <n>
   ```

   Pass `--no-embed` if they want no paid embeddings. If the run stops as
   budget-exhausted, ask again before running the printed resume command; the
   cap is cumulative across resumes.

5. **Report what is left.** The run prints each remaining finding with its
   class. For `operator_required`, relay the instruction (for example the
   #5413 quarantine commands in `docs/guides/repair.md#quarantine-self-captured-corpus-files`,
   or `gbrain upgrade` on a host that `writer_version` names). For
   `unsupported`, tell the user it is known and cannot be cleared yet.

6. **Verify.**

   ```bash
   gbrain doctor --remediation-plan         # no repair steps left
   gbrain sources writer status --json      # writer versions per host
   ```

Optional, only if the user asks: `gbrain sources writer lock` stops agents
from claiming, activating or transferring writers on this brain until the
operator runs `gbrain sources writer unlock`. See the writer admin lock in
`docs/architecture/topologies.md`.
