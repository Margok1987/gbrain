# Upgrade to v0.59.15.0: write database-only timeline history back into pages; stamp visibility on derived pages

This release completes the v0.59.14.0 containment. Timeline entries that exist
only in the database are now written back into their page as ordinary bullets,
each preceded by a comment line `<!-- gbrain:materialized v1 <hash> -->`, the
next time the page is saved. Extracted atoms and synthesized concepts now
record an explicit `visibility` taken from their origin. Two host-side repair
commands fix pages that are never saved again. There is no schema migration.

1. **Upgrade every process that writes to this brain** (`gbrain serve`,
   autopilot and job supervisors, session hooks, every global CLI install), as
   in v0.59.14.0. Each runs `gbrain upgrade` and is restarted.

   ```bash
   gbrain --version          # expect 0.59.15.0 on every writer
   ```

2. **Run one full doctor pass (not `--fast`) and relay the two new signals.**

   ```bash
   gbrain doctor --json
   ```

   - `timeline_history` counts timeline entries that exist only in the
     database. `details.count` says whether the number is `exact` or a
     `lower_bound` (the scan stops after 2,000 pages or 10 seconds).
     `kept_unrenderable_rows` are entries that cannot be written as a bullet
     without changing them (for example an empty source); they are kept as-is
     and need no action.
   - `derived_visibility` counts atoms and synthesized concepts without an
     explicit visibility, or stored looser than their origin. Remote readers
     already treat all of them as private.

   Health scores may drop by these warnings until the repairs below run.

3. **Preview the repairs, then apply them on the brain host.** Both are dry
   runs unless `--apply` is passed. Show the user the preview first; it prints
   the resolved brain and sources, the pages affected, and the request-ID cost.

   ```bash
   gbrain repair                          # preview every kind
   gbrain repair timeline --apply         # write database-only entries back into their pages
   gbrain repair visibility --apply       # stamp explicit visibility, tighten-only
   ```

   Add `--source <id>` to limit a run to one source and `--limit <n>` to repair
   in batches; rerunning the same command resumes where it stopped. If a run
   stops near a journal capacity limit, it prints the exact
   `gbrain config set persistence.limits.<key> <value>` that lets it finish;
   ask the user before raising a limit. If it reports that the writer is held,
   inspect `gbrain sources writer status <source>` and rerun. A thin client
   refuses `gbrain repair`; the brain host operator runs it.

4. **What changes for the user.** Saved pages may gain marked bullets for
   history that previously existed only in the database; this is expected.
   Deleting such a bullet with a `put_page` that passes the current
   `expected_revision` deletes its entry. A save without a revision, and a
   connector refresh, keep marked entries and write them back. The visibility
   repair never loosens anything: atoms from transcripts or from pages that no
   longer exist become private.

5. **Verify:**

   ```bash
   gbrain repair --json                   # every kind reports 0 items
   gbrain doctor --json                   # timeline_history and derived_visibility ok
   ```
