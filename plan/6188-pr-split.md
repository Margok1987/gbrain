## PR1: failure isolation (a fence defect never blocks a sync)
- Typed refusals at every fence refusal site: the three master `fenceError` sites, wave 10's quoted-fence refusal, `take_row_collision` (reason `stored_row_collision`, keeps its wire code), the withdrawal guard (`withdrawn_claim_in_malformed_fence`). Canonical code `invalid_fence` with a reason; wire `error` stays `invalid_params` (E3) so connector item holds keep treating it as content. `CODES` entry in `error-registry.ts`, `ERROR_CATALOGUE` entry, `LEGACY_CONTENT_MESSAGES` for the old messages, `isContentRefusal`.
- Durable structured payload: fence location/reason in a bounded, versioned field of the receipt's error detail (remote-filtered); compacted legacy failures convert only by re-screening current bytes; an arbitrary `invalid_params` is never a fence hold.
- Screen fence step with modes (E8): `screenImportContent({ fences: 'coordinated' | 'lenient' })`. Coordinated (managed sync freeze+prepare, managed import, `managed_file_repair`, coordinated put_page): any strict-parser warning, repeated marker or cross-section row collision → refused `invalid_fence` with a location-only message (fence, section, reason; no row text). Lenient (legacy paths): unchanged behavior (T5). No normalization in PR1.
- Holds: `GitHoldCode` `invalid_fence`; `GitHoldMeta.fence` (location-only: fence, section, reasons, rows when derivable without cell text) and `fence_version`; one shared re-screen predicate (blob change, retry-held, `fence_version` older) for managed discovery and legacy `planHoldRescreen` (E23).
- Conversions: hold-from-receipt when the re-screen admits the same bytes but the failed receipt is a fence refusal (reason `prepare_time`); same-run conversion at the terminal-failure branch of the managed sync loop (single and bulk paths), with a bounded wait for in-flight lane requests and `partial` otherwise (E10). Forced probe: a body that passes the screen and fails in preparation finishes `synced` in ONE invocation with one hold.
- One hold-repair router (D6): every surface (sync `holds_fix`, `held-reads` remote fix, `heldFileDiagnostic`, doctor `git_held_files`, post-upgrade banner, `sources retry-held`, file-repair messages, help text) maps hold code → next step. For `invalid_fence` in PR1 the next step is: read the page (`gbrain get --source <id> -- <slug>`), edit the named fence, then `gbrain sync --source <id> --no-pull` (PR4 switches it to `gbrain repair fences`). Never frontmatter advice. Remote callers get `tell_user_to_run` (owner handoff).
- `sync --dry-run` lists fence holds in `would_hold`. Company-brain sources keep failing closed (UC3) with the typed fence refusal and the commit-upstream fix; `sync.holds=fail` blocks with the typed code.
- Docs/notices: `error-codes.md`, `live-sync.md` hold paragraph, `write-refusals.md` anchor, troubleshooting row, AGENTS.md held-file bullet, BEHAVIOR_CHANGES row, migration note, CHANGELOG, KEY_FILES.
- Tests: managed sync (PGLite + Postgres) with a malformed fence among clean files finishes `synced` with one hold visible in `sources status`; the forced screen-pass/prepare-fail probe in one invocation; a pre-upgrade blocked cursor with a legacy `invalid_params` fence receipt converts without `--retry-failed`; bulk-lane failure mid-group; connector item hold treats it as content; dry run; company and `sync.holds=fail`; router text for every surface; privacy sentinel (no claim/holder/kind text in holds, refusals, receipts, results, logs).
